## 3. 保存形式を先に固定する

初期版ではDBをv8、JSONをv6にする。着手時に既に番号が進んでいたら、衝突しない次の番号を使い、文書にも記録する。

### 3.1 豆に追加する項目

`purchaseDate: null | 'YYYY-MM-DD'`

- 旧データはすべて `null`。登録日・焙煎日から補完しない。
- 新規登録でも初期値は空欄。「購入日（任意）」と「今日」ボタンを追加する。過去の在庫入力を当日購入にしないための設計。
- 編集で未指定なら既存値を保持し、明示的な空欄保存で `null` にする。
- 実在する日付かつ入力時の今日以前。焙煎前の予約購入もあり得るため、焙煎日との前後関係では拒否しない。
- 詳細画面に表示し、通常一覧には表示しない。アーカイブの編集でも変更できる。
- CSVは既存列の順序を維持して末尾に `purchaseDate` を追加する。
- バックアップ読込時は既存の未来日許容方針に合わせる。端末日付の違いで正当なバックアップを拒否しない。

### 3.2 プリセットに追加する項目

| 項目 | 型・初期値 | 意味 |
| --- | --- | --- |
| `reserveBags` | 0〜20の整数、初期値0 | 維持したい未開封袋数。0は手動補充通知を無効にする。 |
| `allowedRoasts` | 1〜5の重複なし昇順配列、初期値 `[1,2,3,4,5]` | 発見候補に使える焙煎度。空配列は発見候補から外す。 |

初期名 `ブレンド｜フジタコーヒー` と旧名 `ブレンド フジタコーヒー` に完全一致する既存／新規初期プリセットのみ、移行・初期作成時に `[3]` を設定する。改名済みの豆を推測して特定しない。設定画面でユーザーが修正できるようにする。この制限はおすすめ候補にだけ適用し、既存の豆登録や過去履歴を拒否・変更しない。

`savePreset` は現在 `{id,name,order}` を作り直す。名称編集でも上記設定を保持するよう変更する。並べ替え、改名、削除後にも他のプリセット設定を失わないこと。

### 3.3 全体設定

IndexedDBに `settings` ストア（keyPath: `id`）を追加し、次の1レコードを持つ。

```js
{ id: 'recommendations', observationStartDate: null, leadDays: 14 }
```

- `observationStartDate` は `null` またはローカル日付。自動では開始しない。
- 設定画面の「今日から消費ペースの記録を始める」で今日を保存する。「以後、飲み切った袋を続けて記録してください」と説明する。
- 初期版に過去への変更・開始日のリセットUIは作らない。記録前の不完全な履歴を推定に使わないため。
- `leadDays` は1〜60の整数。UIは「何日分以下になったら購入候補にするか」、初期値14。
- `snapshot()` は `{beans,presets,recommendationSettings}` を返す。最後の値は `id` を含まない `{observationStartDate,leadDays}`。ストアレコードとの変換はDB層で行う。
- `getRecommendationSettings()` と `saveRecommendationSettings(input)` を追加。保存失敗時に成功表示しない。

### 3.4 バックアップ互換性

v6のトップレベルは `schemaVersion, exportedAt, beans, presets, recommendationSettings`。新規フィールドの型・範囲・余分なキーも検証する。

v1〜v5の読込を維持し、旧版には上記初期値を付与してv6相当へ正規化する。古いバックアップを復元した場合、現行設定を混ぜず初期値に置き換える。`replace` はbeans・presets・settingsを同一トランザクションで全置換する。不正入力で一部だけ消えないこと。

`serializeBackup`、`parseBackup`、復元前バックアップ、設定画面の説明・復元確認表示も追随させる。v6→書出し→復元で新規項目が一致すること。

## 4. 補充候補の計算仕様

新規 `recommendations.js` にDOM・DBを扱わない純粋関数を置く。計算には引数 `currentDate` を渡し、関数内部で現在日時を取得しない。

豆をプリセットに解決する際は、有効な `presetId` を優先し、なければ現行 `matchingPreset` と同じ完全一致名で解決する。曖昧一致はしない。削除済み／自由入力だけの豆は今回のプリセット別おすすめから除外する。

### 手動補充ルール（履歴ゼロでも動く）

- 未開封数 `U`：対象プリセットの `status==='active' && openedDate===null` の袋数。
- `reserveBags > U` なら候補にする。
- 表示例：「未開封0袋／目標1袋。あと1袋で目標に届きます」。不足数は `reserveBags - U`。
- 開封済みと日付不明は未開封数に含めない。

### 消費履歴ルール（観測開始後に動く）

1. 観測開始日が未設定なら計算せず、設定へのリンクを表示する。
2. 観測期間は開始日と「今日から89日前」の遅い方から今日まで、両端込み最大90日。今日より後の開始日なら計算せず端末日付の確認案内を表示する。
3. `finishedAt` を端末のローカル日付へ変換し、期間内かつ `status==='archived' && finishedReason==='consumed'` の袋だけを数える。未来の終了記録は除外。
4. 豆ごとに観測期間30日以上、期間内の消費3袋以上を満たすときだけ計算する。それ以外は「記録を蓄積中」。
5. `dailyRate = 消費袋数 / 観測日数`。現在の在庫総袋数（開封済み含む）を `A` とする。
6. `estimatedDays = A / dailyRate`。`estimatedDays <= leadDays` の場合に補充候補へ加える。
7. 開封中も1袋として数えるので残量を多めに見積もり得る。画面に「袋数からの目安です。開封中の残量は反映していません」と表示する。「あと○日で確実になくなる」などの断定は禁止。
8. 表示は「直近○日で○袋消費／在庫○袋／在庫は約○日分」。表示日数は四捨五入するが、候補判定には丸め前の値を使う。

手動と履歴の両方に該当した場合は1枚のカードに理由を併記する。手動不足ありを先、その中では不足袋数の多い順。残りは推定日数の少ない順。同順位はプリセット順。全候補を表示する。

候補がない状態とデータ不足を区別する。手動候補があれば観測未開始でも表示する。購入日・焙煎日・開封から終了までの期間を消費速度の代用にしない。

## 5. 発見候補の計算仕様

履歴件数は購入日の有無にかかわらず在庫・アーカイブの全記録から数える。これは実際の購入回数と同一ではないので、表示は「記録上初めて」「記録が少ない組み合わせ」にする。

- 候補集合：全プリセット × `allowedRoasts`。自由入力焙煎度を新しい数値焙煎度に変換しない。
- `beanCount`：そのプリセットの全記録数。自由入力焙煎度も含む。
- `comboCount`：そのプリセットかつ `roastType==='scale'`、該当焙煎度の全記録数。
- 同じ豆・同じ数値焙煎度の在庫が1袋でもある組み合わせは候補から除外する。
- 重み：`1 / ((1 + beanCount) * (1 + comboCount))`。累積重みによる抽選で、復元なしに最大2件選ぶ。
- 1件目を選んだら、別のプリセットの候補が残る場合は同じプリセットを2件目から除外する。他のプリセットがなければ別焙煎度を許可する。
- 1候補なら1枚、ゼロなら「現在おすすめできる新しい組み合わせはありません」。条件を勝手に緩めない。
- 2枠を「いつもの豆」と「意外な豆」に固定分類する機能は後回し。初期版は上記の共通抽選だけにする。

候補を画面往復や再読込で変えないため、ローカル日付＋更新カウンターから決定的な擬似乱数を作る。更新カウンターは `sessionStorage` の日付付きキーに保存し、「別の候補を見る」で加算する。保存できない環境はメモリにフォールバックする。データが同じなら同一日・同一カウンターで同じ結果にする。候補の列挙順はプリセットID、焙煎度の順に固定し、計算関数には乱数関数を注入してテスト可能にする。

候補は毎回最新データから再計算し、削除済み・在庫追加済み候補を残さない。別候補が十分ある場合でも抽選結果の再出現は許容し、「必ず新候補」と表示しない。

## 6. 画面・操作の具体仕様

- ナビは同じ幅の4項目。タップ領域の高さ44px以上、選択中は既存どおり `aria-current="page"`。
- おすすめ画面では在庫総数、在庫操作ドック、豆追加フローティングボタンを表示しない。
- 各候補は豆名、必要なら焙煎度（1〜5の数字）、理由のみ。実購入前に在庫登録してしまうボタンや購入リンクは追加しない。
- おすすめ設定画面の選択中タブは「設定」。戻り先として「おすすめに戻る」リンクを置く。
- 設定画面には観測開始状態、`leadDays`、プリセット別設定を置く。各プリセット名を押すと編集項目が開く省スペース形式にする。
- プリセット別の入力は未開封の目標袋数と、焙煎度1〜5のチェックボックス。保存ボタンとエラー表示を用意する。
- 設定入力中に `refresh()` が自動再描画して入力を消さないようにする。既存の未保存変更確認・保存中操作制御に接続する。
- 豆名等のユーザー入力は既存 `escape()` 相当でエスケープし、HTMLとして挿入しない。
- 320／390／440px幅で横方向にはみ出さない。在庫ドックの右寄せ・不透明な選択面・余白透過・下部ナビとの間隔を変えない。
- 空データ、プリセットゼロ、候補ゼロ、読込失敗、保存失敗を個別に扱う。

## 7. 作業順序と各ステップの終了条件

### D. 計算処理

`recommendations.js` と `tests/recommendations.test.js` を追加。4・5章を純粋関数で実装する。次の固定ケースを最低限検証する。

| 入力 | 期待結果 |
| --- | --- |
| 目標1、未開封0、開封済み2、観測未開始 | 手動不足1袋を表示。履歴推定は出さない。 |
| 目標1、未開封1 | 手動補充候補なし。 |
| 観測30日、消費3、在庫1、leadDays14 | 約10日分として履歴候補。 |
| 同じ履歴で在庫2 | 約20日分なので履歴候補なし。 |
| 観測29日、消費3／観測30日、消費2 | どちらも蓄積中。 |
| 期間内に譲渡・廃棄・区分不明がある | 消費袋数に加えない。 |
| 開封日unknown／月末／ローカル日付境界／未来記録 | 未開封と誤認せず、暦日と期間境界が正しい。 |

| 同一組み合わせの在庫あり | その組み合わせは発見候補にしない。 |
